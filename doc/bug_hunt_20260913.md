# Server and client bug hunt — 13 September 2026

Three defect groups were fixed. The character-server fix is deployed on
`192.168.10.18`; the unidentified-headgear repair is installed in this Windows
client and takes effect on its next launch. The client archive-merging fix is in
the project source. Existing unrelated workspace changes were preserved.

## Confirmed defects and fixes

### BH13-01: SQL read failures could become partial inventories and duplicate items

`char_memitemdata_from_sql()` stopped reading when `SqlStmt::NextRow()` returned
an error, then reported success with the rows read so far. Its save counterpart
also treated a read error as normal end-of-data. It subsequently inserted the
unmatched items and returned success, allowing the inventory transaction to
commit and the reform protocol to acknowledge it.

The reproduction used the actual previously deployed character-server object
files and SQL implementation against a disposable MariaDB database. Its inventory
table used the production schema. Two synthetic items were saved normally, then
the second row's amount was set to 32768. The SQL column permits that value, but
the in-memory item amount is a signed 16-bit integer, so fetching it reports data
truncation.

| Observation | Previously deployed code | Patched code |
|---|---|---|
| Loading the two SQL rows | Reported success with one item | Rejected the incomplete load; returned no partial items |
| Saving the known valid inventory while the bad SQL row remained | Reported success; SQL grew from two rows to three | Reported failure; both original SQL rows remained unchanged |
| Retrying after repairing the synthetic row | Not required for the original reproduction | Normal load and save succeeded with two rows and preserved metadata |

The fix reads and validates the complete result before making any SQL changes.
Loads reject fetch errors and excess rows instead of silently truncating them.
The save-side `bound` column binding was also corrected from four bytes to the
one-byte field it targets; the old binding overlapped the adjacent unique ID.
No existing production rows were found with the checked numeric overflow values.

The same production-function regression covers inventory, cart, personal storage,
and guild storage, including failed first/later reads, a pending modification
before a later read failure, empty and full inventories, excess rows, and item
metadata. The final fixture reports **40 failing assertions out of 60 before the
fix, and 60/60 passing afterward**, under AddressSanitizer and UBSan.

Evidence: [real MariaDB comparison](../../bughunt-20260913/storage-runtime-report.json),
[original runtime log](../../bughunt-20260913/storage-runtime-before.log),
[patched runtime log](../../bughunt-20260913/storage-runtime-after.log),
[original function regression](../../bughunt-20260913/storage-fetch-before-final-fixture.log),
[passing regression](../../bughunt-20260913/final/logs/storage_sql_failure_test.log).

### BH13-02: Case variants broke archive merge priority

The repair-archive merger treated `data\Enchant\EnchantList.lub` and
`data\enchant\enchantlist.lub` as different resources. It emitted both payloads,
despite the case-insensitive resource lookup, leaving an obsolete lower-priority
copy in the merged archive.

Merging now compares ASCII case while retaining the first archive's payload and
original filename bytes. Legacy Korean bytes are preserved. Both new regression
cases failed before the fix; all six archive-stack tests now pass. The installed
archive scan found no existing duplicate paths, so no active GRF needed rebuilding.

Evidence: [failure](../../bughunt-20260913/client-merge-before.log),
[passing tests](../../bughunt-20260913/final/logs/client_archive_stack_test.log).

### BH13-03: Twenty headgear entries referenced a missing unidentified resource

Cancer Diadem/Crown (5581, 5582) and the eighteen Time Dimensions Rune Crowns
(400529–400546) referenced an unidentified helmet resource absent from the active
archives. The installed compatibility module changes that one field to the
existing standard Helm resource used by item 2228. Its inventory icon, collection
image, and SPR/ACT pair were all located and verified in `data.grf`.

Native Lua loaded all **26,907 item records**. Comparing the installed loader
before and after confirms exactly twenty `unidentifiedResourceName` changes;
every other field and record remained unchanged. The repair is idempotent and
preserves independently corrected resource names.

Evidence: [installed comparison](../../bughunt-20260913/installed-client-verification.json),
[resource paths](../../bughunt-20260913/helmet-resource-evidence.json),
[installed loader regression](../../bughunt-20260913/final/logs/client_resource_repair_test.log).

for 1,617 server-defined item IDs before the twenty-item repair. This is a

for every catalog row. Unrelated artwork was not substituted.

navigation preview issue were not verified in this pass. The Prontera preview
payload itself is readable and its original bytes remain unchanged; that alone
does not establish why the game previously displayed “No Image.” The two
monster Attack2 warnings are the existing explicit 65535 engine cap, not new
startup errors; no combat values were retuned.

## Deployment and rollback

Deployment finished at **12:27:07 Bangkok time** with no players online. It
replaced only the character executable and its changed C++ source. Login, map,
and character services were briefly stopped and restarted; startup and their
handshake passed. Database and web services remained running. No database schema
or player record was changed.

All **112 inventory rows** retained the same complete serialized hash across the
restart. Cart, personal-storage, and guild-storage tables were empty and also
retained their hashes. Ports 6900, 6121, 5121, and 8888 were reachable afterward.
The actual running character executable matches the tested candidate:
`56aff5f058ac7fd4f670792651a88f1f66d25279fd51a32347a879cb87e195b4`.

The [deployment receipt](../../bughunt-20260913/deployment/report.json) records
the file and table hashes. Server rollback files and the 22,753,312-byte complete
database backup are retained at
`/app/rathena-builds/bughunt-20260913/deployment/`. The directory is root-only and
the SQL dump is mode 0600. Ordinary rollback should restore only the previous
character source and executable during maintenance; restoring the database
would discard later player changes and is not needed for this code fix.

The Windows loader backup is
`server-work/bughunt-20260913/client-backup/itemInfo.lua`. Restore it and remove
`SystemEN/ItemResourceRepair.lua` to undo this client change, provided no subsequent
loader edits have been made. The installation receipt records both loader hashes.

The disposable SQL containers, their data volumes, and their internal test
network were removed. The stopped build container and source/evidence directory
were retained. No SSH password was written to project or evidence files.
